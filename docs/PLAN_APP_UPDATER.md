# 应用内更新功能设计（Mirror Updater）

状态：**待你放行**。这轮只出设计，不动代码。你提的关键问题——"每次更新要不要重装、数据会不会受影响"——是本方案的主轴。

## 一、事实底座（本轮实测/核对）

1. **数据与安装位置天生分离**（这是好消息，决定了"无影响更新"可行）：
   - SQLite 索引 + 设置：`%APPDATA%\dev.multicloud.publisher\publisher.sqlite3`（由 identifier 决定，**与安装目录无关**）
   - 密钥：Windows 凭据库（同样与安装目录无关）
   - 程序本体：`D:\Mirror Cloud\`（NSIS perUser 装在 LOCALAPPDATA，我们历史上改到了 D 盘）
   ⇒ **换 exe 不动这两个目录 = 用户零感知**。今天矩阵已实证：覆盖安装后配置、token、Typora 链全部原样可用。
2. **发布通道现状**：GitHub Release `v1.4.5`，资产带 sha256（`SHA256SUMS.txt`），未认证 API 可读——检查更新的接口天然免费存在。
3. **Tauri 官方 updater 插件不可用的原因（要如实说）**：它要求 minisign 签名（私钥进 CI、pubkey 进配置），且 Windows 走"下载 MSI→静默 msiexec 替换"路径；我们没有签名密钥体系，引入它=新增一整条密钥管理面。**不选它 ≠ 做不到更新**，见下。

## 二、方案对比（为什么选 A）

| | A. GitHub Releases 自研薄更新器（选它） | B. 官方 updater 插件 | C. 什么都不加，维持手动 |
|---|---|---|---|
| 新依赖 | 0（复用 reqwest+serde 现有栈，Rust 侧 ~150 行） | tauri-plugin-updater + minisign 密钥对 | 0 |
| 密钥管理 | 不需要（用已有的 sha256 校验） | 需要生成并永久保管 minisign 私钥，CI 泄露面+1 | — |
| 数据保留 | ✓（见三） | ✓ | ✓ |
| 平台 | 只 Windows（本项目唯一出货平台） | Win/mac/linux | — |
| 代价 | 版本比较/资产挑选逻辑自己写、自己测（可进门禁） | 供应链多两环，且插件版本被 tauri 家族锁（2.11.1 JS vs 2.11.5 Rust 的家族门会咬） | 没有产品化更新 |

C 是现状但不是终点——你提的就是这个需求。**A 的诚实弱点**：sha256 防篡改不防冒充（冒充需要攻陷 GitHub 仓库或 TLS，那时 minisign 也只是多一道）。若你以后要做正式签名（ Authenticode / minisign），A 的检查-下载-校验骨架可以原样接上，不白做。

## 三、更新流程设计（"重装但用户看不见"）

```
[检查] GET releases/latest (api.github.com) → tag_name 与内置版本比较（semver，去掉 v）
      ├─ 无新版 → 报"已是最新 v1.4.5"
      └─ 有新版 → 展示 changelog 摘要（release.body 截断）
[下载] 选资产：*-windows-x64-setup.exe（挑不到就报错，绝不瞎选 msi/zip）
      下到 %TEMP%\mirror-updates\，边下边显示进度
[校验] 同批下载的 SHA256SUMS.txt → 本地重算比对；不一致 = 删除+报错，绝不启动
[安装] spawn setup.exe /S /NS（就是今天验证过的静默通道）→ 退出应用
      NSIS 就地覆盖 D:\Mirror Cloud\ 的 exe；APPDATA 与凭据库根本不碰
[重启] 提示"更新完成，可重新打开"（不自动拉起，避免半初始化状态）
```

**回答你的两个问题**：
- "每次更新都重新装？" —— 引擎层面是的（整包覆盖，8MB 而已），**体验层面不是**：点两次按钮，不用离开应用、不用开浏览器。
- "数据什么的都在？" —— 在。SQLite/凭据/设置在 APPDATA 和系统钥匙串里，安装器从不读写它们（今天的覆盖安装已实证）。Typora 命令里的路径也不用变——安装目录固定。

## 四、UI 与入口

- 设置页「关于与更新」卡（沿用现有卡片形状）：当前版本 · [检查更新] 按钮 → 状态机五态（空闲/检查中/有新版/下载中带进度/失败可重试），全部走既有吐司+内联错误通道，无装饰按钮。
- 不做自动后台轮询（省一次"谁替我决定弹通知"的争议），手动点击起步。

## 五、门禁怎么长（这仓的规矩）

1. `check_user_flow.py` 新增断言：更新器资产选择谓词（setup.exe 正则必须恰好匹配一个已知资产名）、版本比较夹具（1.4.5<1.4.6 / 相等 / 更大 / 垃圾字符串四面）。
2. 校验步骤配变异位（M32：摘掉 sha256 比对必须被抓）。
3. UI 面进 theme_face_inventory / contrast-tier 常规扫描。
4. 网络调用只在用户点击后发生；就绪判据带 timeout（记忆规矩：地址不许兜底写死）。

## 六、工作量与顺序

Rust 侧 commands/updater.rs ~150 行 + 前端一张卡 ~60 行 + 门禁两处；**零新依赖已核实**：
`reqwest 0.13 / sha2 / hex / tokio(fs,net,time)` 都已是 workspace 成员且 src-tauri 已引用 reqwest+sha2。
分两笔：先"检查+下载+校验"（安全侧闭环），第二笔再接"安装+重启提示"。

**网络通道前提（实测）**：这台机直连 `api.github.com` 通、`github.com/releases` 下载要代理（Clash 7897）。
更新器代码走系统代理设置（用户开加速器即好，与 Typora 显示图片同一前提）；失败态文案会明说"检查网络/代理后重试"。
